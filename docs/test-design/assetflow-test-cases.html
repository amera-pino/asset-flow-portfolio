Foundation

基本方針

台帳全体の目的、運用ルール、分類軸をまとめて確認できる入口にする。

基本方針

目標はカバレッジ率の達成ではなく、重要な業務ロジックの欠落を防ぐ。 カバレッジは未テスト箇所の発見には使うが、数値のためのテスト実装は優先しない。

運用ルール

ファイル単位より業務機能単位で台帳を育てる。 テストコードの保守コストが高すぎる場合は粒度を見直し、資産として維持できる範囲で増やす。

台帳の分類軸

フロントエンド単体テストとバックエンド単体テストは同じ業務機能名で並べる。 横断テストは結合、E2E の順で整理し、ハッピーパスに絞って実施する。

参考にした考え方

このテスト方針は、GitLab の testing strategy / testing levels、 Google Testing Blog、Martin Fowler の test coverage / test pyramid の考え方を参考に整理した。 低いレベルのテストから始めること、重複を避けること、E2E は重要導線に絞ること、 coverage を数値目標そのものとして扱いすぎないことを重視している。

Unit Tests

単体テスト

フロントエンドとバックエンドで守る責務を分け、壊れたときの影響が大きい振る舞いを優先して確認する。

フロントエンド単体テスト方針

  • 画面ごとの重要な表示ロジック、入力制御、操作導線、APIエラー時のエラーメッセージ表示を優先して確認する。
  • 画面の実装方法そのものに強く依存する確認は増やしすぎず、利用者に影響の大きい振る舞いを中心に実装する。

フロントエンド単体テスト実装方針

  • React Testing Library と jsdom 上で画面をレンダリングし、ブラウザに近い DOM 環境で利用者操作を再現して確認する。
  • API呼び出しは MSW でレスポンスをモックし、画面表示・入力・状態変化を単体で検証する。

バックエンド単体テスト方針

  • 業務ロジックを持つ service 層を重点的に実装する。
  • 業務ルール、在庫判定、状態遷移、競合判定のように、壊れると影響が大きい箇所を優先して確認する。
  • route 層は正常系と主要なエラー変換を確認し、models / schemas / constants は重要なバリデーションや変換に絞って実装する。

バックエンド単体テスト実装方針

  • pytest で route 層と service 層を確認する。
  • DB はモックではなく in-memory SQLite を使用し、各テストで必要なデータを fixture / factory により投入して検証する。
  • 外部依存を増やさず、CI 上でも安定して実行できる構成を採る。
Cross Tests

横断テスト

結合テストと E2E の役割と実装方針を分けて、どこをモックし、どこを実環境寄りに確認するかを整理する。

結合テストの役割

結合テストは、代表的なハッピーパスの正常系に絞って、各機能観点を確認する。

  • 画面と API の連携
  • API と DB の接続
  • 主要な画面遷移

結合テストの実装方針

結合テストは、下記の構成で実施する。

  • 画面は React Testing Library 上でメモリ内に描画し、利用者操作を再現して確認する。
  • フロントエンドは React アプリケーションの画面遷移と主要操作を確認する。
  • バックエンドは FastAPI アプリケーションを使用し、API と業務処理の接続を確認する。
  • DB は in-memory SQLite を使用し、テストデータを投入して確認する。
  • テストデータは seed CSV を基準とし、結合テストと E2E テストで共通化する。

結合テスト構成図

E2Eテスト（自動）の役割

  • E2E テスト（自動）は重要導線に絞り、一般ユーザーと管理ユーザーの観点で実施する。

E2Eテスト（自動）の実装方針

E2E テスト（自動）は、基本的に結合テストと同じ構成で実施するが、下記の差分がある。

  • 画面操作は Playwright で自動化する。
  • DB はコンテナ上で起動した PostgreSQL を使用し、seed CSV を再投入したうえで、ケースごとに独立して実施する。
  • 詳細な初期化手順と実行手順は、playwright-e2e-architecture.html を参照する。

E2Eテスト（手動）の役割

  • E2E テスト（手動）は、リリース前の最終確認として、本番相当の利用者操作と業務導線を確認する。
  • 自動テストでは拾いにくい表示崩れ、操作感、権限制御、運用上の違和感を確認する。

E2Eテスト（手動）の実施方針

  • E2E テスト（手動）は、本番相当環境または公開環境で実施する。
  • 実施対象は重要導線を中心とし、一般ユーザーと管理ユーザーの主要操作を確認する。
