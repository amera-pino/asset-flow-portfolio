1. 目的

このメモは、AssetFlow の一般ユーザー向け E2E テストを Playwright で実装する前に、 構成方針、責務分担、初期化方針を整理して残すための文書です。

2026年8月4日（火）時点では、E2E の主目的を次のように置きます。

  • 実ブラウザで一般ユーザーの主要業務導線を通せることを確認する
  • ポートフォリオとして、利用者が何を操作し、何が画面上で完了するのかを説明できる状態にする
  • 単体テスト、結合テストと役割を分け、E2E では API ステータス確認より業務フロー確認を優先する

2. 前提

  • フロントエンドは frontend 配下の React + TypeScript + Vite 構成である
  • バックエンドは backend 配下の FastAPI 構成である
  • ローカル起動はルートの docker-compose.yml を使う
  • E2E はブラウザから実データを操作するため、各ケースの実行前に DB 初期化と seed 再投入が必要である
  • E2E シナリオは docs/test-design/assetflow-test-cases.html の E2Eテスト タブで管理する

3. 推奨構成

Playwright は frontend 配下に置きます。

理由は次のとおりです。

  • 実行主体がブラウザ UI であり、フロントエンドの依存管理と近い場所に置く方が自然である
  • package.json、vite、フロントエンド用スクリプトとまとめて管理しやすい
  • このプロジェクト規模では、E2E 専用ワークスペースを別途切るよりも運用負荷が低い

想定ディレクトリは次のとおりです。

frontend/
  package.json
  playwright.config.ts
  tests/
    e2e/
      general-user-loan-flow.spec.ts
      auth-access-control.spec.ts
      pending-request-cancel.spec.ts
      loaned-request-return.spec.ts
      fixtures/
        e2e-test.ts
      helpers/
        auth.ts
        reset.ts
        selectors.ts

4. 責務分担

4.1 spec ファイル

spec ファイルとは、1 本の E2E テストケースをブラウザ操作として実装するためのファイルです。 このファイルには、台帳に書いた 操作 と 確認 を、できるだけその順番のまま実装します。

  • 画面操作
  • 表示確認
  • トースト確認
  • 一覧更新確認
  • ログアウト確認

spec 側に、DB 初期化や seed 再投入の詳細を直接書き込みすぎません。

4.2 fixture / helper

fixture / helper とは、複数のテストケースで共通して使う準備処理や補助処理をまとめるためのファイルです。 同じ処理を各 spec に何度も書かないようにするため、複数ケースで繰り返す処理はここへ寄せます。

  • DB 初期化
  • seed 再投入
  • ログイン補助
  • よく使う要素特定処理の共通化
  • 待機処理

E2E のシナリオ本文と、実行環境の準備処理を分離することを優先します。

4.3 アプリ本体

アプリ本体には、E2E 専用の分岐やテスト専用 UI を極力追加しません。

  • 実運用に近い UI をそのまま操作する
  • Playwright で画面上のボタンや一覧行を探すときは、備品名やカテゴリなど、画面に表示されている情報を使って対象を特定する

たとえば、備品一覧で貸出申請ボタンを押すときは、 備品名やカテゴリの表示を手がかりにして、対象の行にあるボタンを操作します。

5. 初期化方針

E2E は状態変更を伴うため、各ケースの独立性を最優先します。

各ケース実行前に、DB を初期状態へ戻したうえで seed データを再投入します。

5.1 初期化対象のテーブル

ここでいう初期状態とは、少なくとも次のテーブルが E2E 実行前の想定状態に戻っていることを指します。

  • users
  • assets
  • asset_loan_requests
  • user_sessions : ログイン中ユーザーのセッション情報を保持するテーブル。未ログイン状態から E2E を始めるため、このテーブルの状態も初期化対象に含める

5.2 DB 初期化手順

各ケース実行前に、下記の DB 初期化と seed 再投入を実施します。

以下の docker compose コマンドは、リポジトリルートをカレントディレクトリとして実行します。

  1. DB コンテナ上のデータを E2E 用初期状態へ戻す
    • users、assets、asset_loan_requests、user_sessions を truncate して、ID 採番も初期状態へ戻す
    • 実行コマンド例:
    • docker compose exec db psql -U assetflow -d assetflow -c "TRUNCATE TABLE user_sessions, asset_loan_requests, assets, users RESTART IDENTITY CASCADE;"
    • このコマンドで、DB コンテナ上の対象テーブルだけを E2E 実行前の空状態に戻す
  2. backend/app/seed_data 配下の seed 用 CSV を再投入する
    • 実行コマンド例:
    • docker compose exec -e PYTHONPATH=. backend python app/seeds.py
    • このコマンドで、マイグレーション確認後に users、assets、asset_loan_requests の seed データを再投入する
  3. seed 再投入後の状態で E2E ケースを 1 本だけ実行する

ケース間で DB 状態を共有しません。

補足: Playwright 実装時には、初期化コマンドまたは fixture 名を固定します。

6. テストケース分割方針

実装対象候補は、次の 4 本です。

  • E2E-001: 一般ユーザー申請動線
  • E2E-002: 一般ユーザー認証・アクセス制御
  • E2E-003: 一般ユーザー承認待ち申請キャンセル動線
  • E2E-004: 一般ユーザー貸出中申請返却動線

この分け方を採用する理由は次のとおりです。

  • 1 本あたりの主目的が明確になる
  • 失敗時の切り分けがしやすい
  • 実装順を柔軟に調整しやすい
  • ポートフォリオ説明時に業務フローを分けて見せられる

7. 実装スタイル

7.1 まずは単純に書く

初期実装では、共通処理を無理にまとめすぎず、まずは 1 本ずつの spec を読めば 「何を操作して、何を確認するテストなのか」が分かる状態を優先します。

  • まずは spec を読めば台帳との対応が分かる状態を目指す
  • ログイン処理や DB 初期化のように、明らかに複数ケースで共通して使う処理だけを先に分ける
  • それ以外の処理は、実装を進めながら重複が増えた時点で共通化を検討する

ここでいう「共通化」とは、同じ処理を別ファイルへ切り出して、複数のテストケースから再利用できるようにすることです。 最初から細かく分けすぎると、どこに何が書いてあるか分かりにくくなりやすいため、初期段階では読みやすさを優先します。

7.2 locator の方針

locator とは、Playwright で「どのボタンを押すか」「どの文字列を確認するか」を特定するための指定方法です。 たとえば、備品名の文字列、ボタン名、見出し名などを使って画面上の要素を見つけます。

対象要素は、可能な限り次の情報で特定します。

  • 備品名
  • カテゴリ
  • 有効在庫数
  • 状態

台帳上で 現行 seed では No.1 のような補足を書くのは許容します。

7.3 実行設定

  • baseURL: process.env.PLAYWRIGHT_BASE_URL ?? "http://localhost:5173"
    • baseURL は、Playwright がブラウザを開くときの起点 URL です。
    • ローカル既定値は http://localhost:5173 です。
    • CI でも現時点では環境変数で http://localhost:5173 を渡し、実行モード内で origin を統一します。
  • workers: 1
    • workers は、テストを同時に何本並列実行するかを決める設定です。
    • 今回は状態変更を伴う E2E が中心なので、まずは 1 にして 1 本ずつ順番に実行します。
    • これにより、在庫数や申請状態の競合で失敗する可能性を減らします。
  • retries
    • retries は、テストが失敗したときに自動で再実行する回数を決める設定です。
    • ローカルでは 0 にします。失敗したらすぐ原因を確認したいからです。
    • CI 導入時は 1 または 2 を検討します。ネットワーク待ちや描画待ちなどの一時的な失敗を吸収しやすくするためです。
  • trace: "on-first-retry"
    • trace は、テスト中の画面遷移や操作履歴を記録する設定です。
    • on-first-retry は、最初の失敗時に再実行したテストだけ記録する設定です。
    • 常時記録よりも保存量を抑えつつ、失敗時に原因を追いやすくできます。
    • ただし、ローカルで retries: 0 の間は再試行が発生しないため、通常は trace は保存されません。
    • ローカルで trace を確認したいときは、一時的に trace: "on" または --trace on を使います。
  • screenshot: "only-on-failure"
    • screenshot は、テスト実行中の画面画像を保存する設定です。
    • only-on-failure は、失敗したテストだけ画像を残す設定です。
    • 成功時の画像を大量に残さず、失敗時の確認に必要な情報だけを保存できます。
  • video: "retain-on-failure"
    • video は、テスト中の画面操作を動画として保存する設定です。
    • retain-on-failure は、失敗したテストの動画だけを残す設定です。
    • 失敗時の再現状況を後から見返しやすくしつつ、不要な動画保存を減らせます。

8. 起動方針

ローカルでは、既存の docker compose up -d を基本にします。

  • db
  • backend
  • frontend

を起動したうえで、通常開発を進める想定です。

E2E 実行時は、Playwright・frontend・backend の origin 方針を同じ値にそろえます。

  • Playwright の baseURL
  • frontend dev server の起動 host
  • VITE_API_BASE_URL
  • backend / frontend の疎通確認 URL

localhost と 127.0.0.1 のどちらを使うか自体は本質ではありません。 大事なのは、1 回の実行で使う origin を全部同じ方針にそろえることです。

ローカル既定では、PLAYWRIGHT_MANAGED_SERVICES が false でない場合に global setup が docker compose up -d db backend frontend を実行します。 readiness check は PLAYWRIGHT_BASE_URL と PLAYWRIGHT_BACKEND_URL を参照し、 未指定時は http://localhost:5173 と http://localhost:8000 を使います。

CI mode では、db と backend を docker compose up -d db backend で起動し、 frontend は VITE_API_BASE_URL=http://localhost:8000 npm run dev -- --host localhost --strictPort で起動します。Playwright には PLAYWRIGHT_BASE_URL=http://localhost:5173 と PLAYWRIGHT_BACKEND_URL=http://localhost:8000 を渡します。 backend の CORS は http://localhost:5173 と http://127.0.0.1:5173 の両方を許可します。

現時点では、認証導線まで含めて安定して通る localhost 系を正本にしています。 ローカルと CI で二系統あっても問題ありませんが、それぞれのモード内では必ず origin を統一します。

9. 実装順

  1. Playwright 導入
  2. playwright.config.ts 作成
  3. DB 初期化 + seed 再投入の fixture / helper 作成
  4. E2E-001 実装
  5. E2E-001 の安定化
  6. E2E-002 以降を順次追加

10. 注意点

  • 各ケースは独立実行を前提にする
  • E2E で API ステータス確認まで厚く書きすぎない
  • 単体テスト、結合テストと責務がぶつかる場合は E2E 側を薄くする
  • 画面に存在しない情報は確認項目に書かない
  • 実装 AI が迷わない具体性を優先する
